## 5. Blocking findings (the smallest concrete repairs required for Gate 2 to re-attempt)

All four independently reproduced by me at the source level in `audit/verify_final_x13_readiness.py` (run it; sections 5-7 are the failing ones).

### 5.1 Evaluator: unguarded `KeyError` instead of fail-closed `SnapshotIntegrityError`

`RetainedSnapshot.from_collector_result` (`src/ebe/evaluator.py:56`): `objects[p.object_id].body` has no existence guard. A packet whose `object_id` doesn't match any entry in `export.body_objects` crashes with a raw `KeyError`, not the typed, catchable `SnapshotIntegrityError` every other integrity fault in this module raises. **Repair:** check `p.object_id in objects` before the lookup and raise `SnapshotIntegrityError` with a clear message if not, consistent with every neighboring check in the same function/`validate_snapshot`.

### 5.2 Evaluator: refcount and "no unreferenced hidden body" are not implemented at all

`FINAL_PRE_X13_FREEZE.md` §2 explicitly requires validating "...exact object bytes, refcounts, duplicate sequence IDs, no unreferenced hidden body...". `RetainedBodyRecord`/`RetainedSnapshot` (`evaluator.py`) carry no refcount field, and the current data model can't even represent an "unreferenced" body (one record is emitted per packet, 1:1). Related: the cap-overflow check (`evaluator.py:111`) only fires when the caller supplies `declared_total_bytes`; a snapshot with real bodies exceeding `capacity_bytes` but `declared_total_bytes=None` passes with zero issues. **Repair:** either implement refcount/hidden-body validation against the real `CollectorResult.retained_export` schema (if it carries this data) and make the cap-overflow check independent of `declared_total_bytes`, or — if the underlying store export genuinely has no refcount concept to validate — update `FINAL_PRE_X13_FREEZE.md` to say so explicitly rather than leave a requirement that's silently unmet.

### 5.3 Manifest: content integrity is recorded but never re-verified

`src/ebe/x13_manifest.py:182,186-188` computes and stores `configuration_sha256`, `omitted_scope_sha256`, `source_hash`/`source_hashes`, and `accounting_fixture_identity` into the manifest at generation time. `validate_manifest()` (`x13_manifest.py:198-216`) never reads any of these four back to re-compare against the live files — it checks `configuration_manifest.csv` by **row count only** (`!= 791`). Demonstrated: a mutated row (same 791 count, different `config_json` content) passes validation silently. This means the authorization artifact's `manifest_sha256` pin does not transitively guarantee the 791 actual row configurations, the raw source export, or the accounting fixtures are unchanged since generation. **Repair:** add `sha256_file(freeze/configuration_manifest.csv) == manifest["configuration_sha256"]` (and the equivalent for `omitted_scope.csv`, the live source files against `source_hashes`, and the accounting fixture against `accounting_fixture_identity`) to `validate_manifest()`.

### 5.4 Runner: real mode never populates 17 required cost/overhead fields

`FINAL_PRE_X13_FREEZE.md` §4.D explicitly requires "synchronized byte-hours... CPU/process time/elapsed/RSS and artifact disk bytes, logical auxiliary memory" for every row. Confirmed directly in `src/ebe/x13_runner.py`'s `execute()`: `payload = {name: None for name in LOGICAL_RESULT_FIELDS}` initializes every field to `None`, and the subsequent `payload.update(...)` calls (lines ~159-206) never assign these 17: `synchronized_peak_s_plus_m`, `combined_byte_microseconds`, `elapsed_seconds`, `cpu_seconds`, `rss_bytes`, `artifact_disk_bytes`, `aux_collector_bytes`, `aux_store_bytes`, `aux_evaluator_bytes`, `pending_index_peak`, `queue_peak`, `coalesced_updates`, `starvation_events`, `dropped_work`, `reused_from`, `feed_metadata_bytes`, `directory_metadata_bytes`. The correct synchronized-accounting function (`accounting.py:93-120`, independently confirmed correct by hand-computation in §2 above) exists but is never called from the runner; per-row process/RSS instrumentation and E-policy queue/starvation/coalescing stats (upstream data exists in `collectors.py:132-140`) are never wired in either. **Repair:** wire `synchronized_accounting(...)` and `result.event_derived_stats` into `execute()`'s payload, and add real per-row `time.process_time()`/wall-clock/RSS/disk-usage instrumentation — these are the mandatory `overhead.csv`/cost-envelope outputs the frozen contract requires; right now `overhead.csv` would be created with a header and no populated rows even in a real run.

### 5.5 Minor: PCD-R15's "pending suppresses repair" is not a reachable code path

`PeriodicCollector._run_repair` (`collectors.py:340-341`) hard-requires `get_response_delay_us == 0`, so `get_body` can never return a pending/delayed response inside a PCD-R15 run, and there is no "suppress repair while pending" logic to verify because "pending" cannot occur. This is a gap between the frozen contract's described requirement and what the current design can even exhibit — worth resolving (either the delay==0 restriction is intentional and the requirement text should say so, or PCD-R15 needs to support nonzero delay so this control is actually meaningful).

### 10.3 Two minor, non-blocking findings from this independent audit (disclosed, not swept under)

1. **`_rss_bytes()` currently never succeeds on real Windows.** Root-caused directly (not guessed): `ctypes.windll.kernel32.GetCurrentProcess` and `ctypes.windll.psapi.GetProcessMemoryInfo` have no explicit `argtypes`/`restype` declared, so ctypes' default 32-bit `int` marshaling silently mishandles the 64-bit pseudo-handle, and the real Windows API call fails with `ERROR_INVALID_HANDLE` (confirmed via `ctypes.get_last_error()` == 6). The code's own failure handling is correct (falls through to the honest `"NA_RSS_UNAVAILABLE_ON_PLATFORM"` sentinel, not a fabricated zero) — this is a missed-measurement bug, not a wrong-data bug. Confirmed the actual fix works: declaring `GetCurrentProcess.restype = wintypes.HANDLE` plus explicit `argtypes`/`restype` on `GetProcessMemoryInfo` reads a real, sane RSS value (~13.5 MB for a small Python process) on this exact machine.
2. **`pending_index_peak` is gated to `event_stats is not None` (E-policy rows only)**, even though `result.peak_dirty_titles` — the value it would use — is a real field populated identically for P/PD/PCD/PCD-R too (confirmed directly in `collectors.py`: the same `peak_dirty`/`dirty` tracking feeds `CollectorResult.peak_dirty_titles` in both the plain `run()` return and `_run_repair`'s return, not just the E-derived path). Non-blocking (the current `NA_NOT_APPLICABLE` is honest, not fabricated), but real, available data is currently left unsurfaced for the majority of rows.

Neither finding violates the frozen contract's actual bar ("no missing payload/overhead imputed as zero" — both fields fail to an honest, explicit NA, never a silent zero or wrong number). Both are worth a follow-up fix, but do not block this verdict.
